# webchat

The chat page a visitor gets in a browser, with no install and no account: join
a station's WiFi, open the page, talk to the mesh. One page, two editions:

| edition | what serves it | where the page goes |
|---|---|---|
| firmware (ESP32 boards) | the station's captive portal | `xprs-dev/firmware`, `common/xprs_hotspot/chat_page.c`, generated by `tool/build.py --c` |
| Android app | the phone's share server | `xprs-dev/app`, `assets/web_chat/`, generated by the app's sync tool |

The page is a pure client of `spec/API-HTTP.md`. The key is made in the browser
and signs real XPRS packets (XPRS.md 9.1.2); the station only validates a wire
and airs it, and never sees a private key.

## Layout

On a narrow screen (a phone held upright) the room list is a drawer: a bar
above the conversation names the room, with a count of the people who wrote
and were not read yet, and opens the same grouped list over the page, where
a hundred private conversations scroll like anywhere else. A tap on a room
closes it. Wider than 640px the list is the column on the left.

- `page/` the source: `chat_page.html`, `xprs_crypto.js`, `xprs_seal.js`, `xprs_nostr.js`, `logo-font.css`.
- `tool/build.py` merges them into one HTML file, gzipped, and optionally the C
  array the firmware embeds. `tool/test_crypto.sh` checks the signing against
  the XPRS.md 9.1.2 worked example.
- `contract/mock_station.py` a station that answers just what the page asks.
- `test/` `smoke.py` loads the built page in headless Chromium against the mock, `dm_smoke.py` drives a sealed direct message through it, `layout_smoke.py` checks the composer stays on screen under Android's bars and toolbars, `seal_test.js` checks the sealing.

## One page, many stations

The page asks `/api/services` and adapts. A station that lists `page` there
says which panels it fills and whether it offers the app:

```json
{ "ok": true, "page": { "tabs": ["chat", "traffic"], "config": false, "app": "/app", "session": true } }
```

`tabs` are the views the station can serve, offered in the menu (`chat`, `traffic`, `devices`,
`stats`, `station`, `settings`); the others are hidden. `config: false` hides
the board's `/config` link. `app` is the path of a page where the app can be
downloaded, and shows a "Get the app" link. `session: true` says the station
gives a visitor who proves their key their own direct messages (below). A station with no `page` (the
boards, today) shows everything and no link, exactly as before.

## The rooms' archive, and Traffic

The page asks each room's archive once, a room at a time
(`/api/xprs/history?kind=message&room=local`, then regional, global and the
Social feed), and after that only the newest rows every three seconds. Asking
the newest 200 of everything gave one room: a bridged Meshtastic channel filled
all 200 and Local and Global looked empty. A station that does not know `room=`
answers its newest messages, which the page files as before.

Traffic shows one entry per packet. The archive keeps a copy per bearer a packet
went out or came in on, so the copies (the same XPRS.md 5 identifier) merge into
one entry with a tag per direction and bearer: `↑lan ↑espnow ↓ble -61`.
`test/traffic_test.js` checks the merge.

## Devices, and a distance through a relay

The Devices tab lists `/api/xprs/devices`. A station a relay carried here
(`+1 hop`) is as far as the relay plus the relay's own reading of it, which
the station sums into `dist_m` (firmware `docs/chat.md`); the row then also
says `via`, `near_m` and `far_m`, and the cell shows the sum with the legs
in its tooltip. When the relay has not yet said how far the station is from
it, the first leg is shown as a floor: `>~12 m via X3SEP2`.
`test/devices_test.js` checks the cell.

## The page in Android's captive-portal browser

Android opens a station's page in CaptivePortalLogin, whose WebView sits in a
swipe-to-refresh layout: a downward drag while the DOCUMENT is at scroll 0
reloads the page, whichever inner panel the finger is on. This page scrolls
only inside its panels, so the document sat at 0 for ever and scrolling up
through the conversation reloaded it. The body is one pixel taller than the
window and parked at `scrollY` 1 (`park()`, and the `html`/`body` rule): the
WebView then reports it can scroll up and the drag stays with the panel. The
document itself cannot be dragged, and `overscroll-behavior` stops a panel at
its end, and Chrome's own pull-to-refresh, from chaining to it. Nothing to
test but on a phone: join the hotspot, open the page from the sign-in
notification, scroll up.

## Direct messages

A direct message is sealed to the peer's key (XPRS.md 6.2, AES-256-CBC under the
ECDH secret) when the page can find a key the station VERIFIED for that
callsign (`/api/xprs/history?kind=identity&call=`), and sent in the clear, with
a note, when it cannot. `page/xprs_seal.js` does it in plain JS because a page
on plain HTTP has no WebCrypto; `test/seal_test.js` checks it against the
FIPS-197 vector and against an `x:` made by the Dart implementation.

Mail addressed to a visitor is shown only to a visitor who proved the key
behind their callsign: `GET /api/session` gives a one-time nonce, the page signs
`t:session f:<call> ts:<stamp> m:<nonce>`, `POST /api/session` returns a session
that `/api/xprs/history?session=` then honours. Anyone can write any callsign;
only the key signs.

## The station's name, the menu, and its administrator

The title reads `XPRS (X3PTZM)`: the station's callsign from `/api/services`
(`station`), or `/api/status` on a host that does not give it there. The menu
(top right) is grouped into the visitor's identity, this station, and this
page, and closes on a click or tap outside it, or Escape.

A station that lists `admin` under `page` has an administrator
(`spec/API-HTTP.md`, `/api/admin`), and the menu offers Administration. With
none yet, a visitor on the station's own network (its WiFi or LAN) who proved
their key can claim it: the moment after a board is flashed or a server
installed. From the internet the claim is not offered. The administrator
chooses whether the Local room is kept from visitors outside the station's
network (on by default; such a visitor sees a note in the Local room) and who
may post from the page (everyone, the station's network, nobody), and can give
the station up.

Where `page.moderation` is set the station's rooms have moderators (XPRS.md
10.10). The administrator appoints them (by callsign), dismisses them, and lifts
a removal; an appointed person accepts in Administration, and the
administrator's own acceptance is signed as they claim. A moderator's message
menu offers "Delete for everyone" (`t:moderate ... r:<id> remove:message`) and
"Send <callsign> away" for an hour, a day or until lifted (`revoke:<call>
[until:]`), signed in the page and posted like any wire; Administration lists
the moderators and the people sent away. What the station reports removed
(`moderation` on the history answer) leaves every page showing it.
`test/admin_smoke.py` covers the menu, this view and moderation.

Where `page.rooms` is set the station hosts closed groups of its own (XPRS.md
10.10.1, `/api/rooms`): the administrator creates them in Administration
(name, about, public or private, anyone or members posting), adds members,
appoints moderators and closes them; the station signs those acts as the room.
They appear in the sidebar under "Station rooms" (a lock marks a private one),
an invited visitor sees a Join button in the room and accepts with their own
signature, and a message there is `d:<room>`, kept on the station and never
aired. Moderators of a room have the same message menu as the station's.

Alerts are a feed entry on the left, under Social: the active `t:warning` and
`t:info` the station holds (XPRS.md 24, 25; active until `until:`, or a day,
and not withdrawn), listed in the conversation column. The entry reads
"Alerts (n)" while there are alerts this browser has not looked at, polled
every thirty seconds. A feed has no composer bar: what there is to add goes
through a round + at the bottom right of the conversation column, which opens
a panel at the top of the feed and leaves it alone while it is open. On
Alerts the + is offered only to whom the station lets post (`page.alerts`,
XPRS.md 10.10.2): the moderators and the administrator, or everyone; the panel
composes a signed warning (kind, severity, how long) or notice, and the author
may withdraw their own.

Blog is the next feed entry: the `t:blog` posts the station holds (XPRS.md
18), newest first, as cards with the title, the text, the author and the
tags. A long post arrives split (7.6) and the archive keeps the parts, so the
page joins them, keyed on author and timestamp (6.6), and never shows one
with a part missing. A later post with the same title from the same author
replaces the earlier (18.1) and reads as edited. The entry counts the posts
this browser has not looked at, polled every thirty seconds. The + writes a
post: a title that becomes a label (18.1) and up to about 1500 characters,
signed by the visitor and sent through `/api/xprs/send` as one packet or as
parts (`splitSigned()`, the same as a forum topic). A station airs each part
as given, so nothing is asked of it beyond the spec: a part carries no
signature of its own and the page joins the set and judges the whole. A whole
post filed by a station that joined the parts itself outranks the parts in
the fold. `test/blog_test.js` checks the fold.

## The banner, and the logo

What the page lets the administrator set about itself goes through one rule
on the station: a setting named `page_<name>` on `/api/admin` is a string of
at most 8000 characters, stored as given and reported as `page.<name>` on
`/api/services`, gone when set to empty. The station knows nothing of what
the names mean, so a new one costs it nothing. The page uses three:

- `page_banner`: HTML under the header for every visitor; none until the
  administrator writes one.
- `page_logo`: HTML in place of the XPRS lettering at the top left, an image
  or text; it still goes home on a click.
- `page_css`: a stylesheet added after the page's own, in `<style id="st-css">`.
  The whole palette is custom properties on `:root` (`--accent`, `--bg`,
  `--text`, `--muted`, `--border`, `--panel`, `--field`, `--line`, `--dim`,
  `--on-accent`, `--own`, `--banner`, `--radius` and a few more at the top of
  the stylesheet), so a colour scheme is one block. Six themes to start from
  (`THEMES`: Orange retro, Clean dark, Cyberpunk, Rose, Paper, Forest) are
  chips above the stylesheet: picking one is the choice itself, applied and
  saved for every visitor at once (a hand-written stylesheet is replaced),
  and the theme's whole block fills the stylesheet below, every property
  named and the default one annotated, to edit and Save again; so a theme
  is nothing to the station. Administration
  redraws itself every minute, but not while a field holds unsaved text
  (`adminDirty`). `test/theme_shots.py` screenshots each theme.

All three are in Administration, under Banner and Look, take effect in the
administrator's own page at once and reach other visitors on their next load.
They are the administrator's own HTML and CSS, trusted as the station is.
The arrow on the banner
minimizes it to its first line and opens it again; the choice is kept in this
browser (`xprs_banner`). Open, it scrolls past about a quarter of the screen,
a third on a phone held sideways. The XPRS logo at the top left goes back to
the chat's Local room from anywhere.

The administrator moderates every room the station hosts: the role the
station offers on each room is accepted by the page as it comes, so no
"Accept moderating" is ever asked of them.

## Forum rooms

Forum is always on the left column, beside Blog. It opens on the station's
forum categories: each a station room of kind `forum` (XPRS.md 18.5; `kind`
on `/api/rooms`), drawn as a card, one click to open. The administrator sees a
round + at the bottom right of the Forum and of a category's topic list; on
the Forum it opens a panel that creates a category (name, about, visibility,
who posts), the same `create` on `/api/rooms` as Administration's New room,
with the kind set. A visitor sees who creates categories, or that the station
has no administrator yet. Its posts are `t:blog` to the room: a titled post opens a topic, replaced by a later one of the same title
from its author; an untitled post naming it with `r:` is a comment. The room
shows its topics as cards from `/api/rooms?topics=<call>` (title, author,
replies, last activity), a topic as the opening post with its comments from
`/api/xprs/history?room=<call>&kind=blog&root=<id>`, and the composer
replies while a topic is open. A new topic is a form above the list: the
title becomes a label, the text up to about 1500 characters. A post longer
than one packet is split at spaces into up to nine parts (7.6) and signed
once over the whole, the signature carried on the last part (9.1.1), which
`splitSigned()` does for topics and comments alike; the station holds the
parts and files the whole once the last one verifies it, so a thread reads
back as posts, never fragments. An author withdraws their own post, a
room moderator deletes any. The administrator picks the kind when creating a
room. The mock serves a forum room with `MOCK_FORUM=1`.

A room can be shared between stations (XPRS.md 10.10.1). In Administration
the owner ticks "Shared with other stations" on a room and names the peer
stations, or leaves the list empty to let any station mirror a public room;
the card then lists the stations that mirror it. "Mirror a room from another
station" takes the room's `X5` callsign and the station that holds it: this
station keeps a copy, asks the owner for what it filed (`sync`, and every
minute when there is news), and the owner asks it back, so a post made on
either side reaches the other. A mirrored room's card says so, offers "Sync
now" and "Stop mirroring", and has no member controls: the mirror never signs
as the room. Sharing a private room asks for confirmation first: served to
members here, it is readable by the peer stations' operators too.

## Private messages

"Private message" (the menu, or the People heading on the left) starts one
with a callsign active on the chat or with an npub, which is the key itself
(its X1 callsign derives from it). A conversation is sealed to the peer's key
by default (`x:`, XPRS.md 6.2); the lock beside the message box switches that
conversation to clear text (`m:`), the only form amateur bands allow (6.4),
and the room says which it is. With no key heard for a callsign the page asks
before sending in the clear; it never does so silently. Callsigns shown in
Administration and on alerts open a private message.

Each person on the left shows how many of their messages are unread,
"X1ABCD (2)", in bold and sorted first; opening the conversation clears it.
What was read is remembered per origin (`xprs_dm_read`), and a browser that
never read anybody counts from its first visit, not the whole archive.

## A NOSTR extension

With a NIP-07 extension (`window.nostr`: nos2x, Alby and the like) the menu offers
"Use my NOSTR extension", and the account is the same on every station: the
callsign comes from the extension's public key, whatever the station. The key
never reaches the page.

- **Signing.** The extension signs only NOSTR events, so a packet is signed in the
  second form of XPRS.md 6.1.3: the page asks it to sign a kind 24767 event whose
  content is the packet digest, and the 64-byte BIP-340 signature goes in `sig:`
  as 80 characters (the short 60-character form stays the default for a key the
  page holds). The extension may ask each time; most let the user allow the kind.
- **Sealing.** `nip04.encrypt` and `decrypt` are the `x:` cipher in another
  wrapping (6.2); `page/xprs_nostr.js` converts, and refuses a signer that
  changed the time or content it was asked to sign.
- **Offered first.** When the page finds an extension (it looks for 3 s, the
  time one takes to inject `window.nostr`) and the visitor has not chosen yet,
  it asks, with "Use my NOSTR identity" as the default answer. A first-time
  visitor gets no key until they answer; "Make a new key in this page" (or, for
  a returning visitor, "Keep <callsign>") keeps the page's own key. With no
  extension the page makes its key silently, as before.
- **Remembered.** The answer is kept per origin (`xprs_ext`: `1` the extension,
  `0` the page's key) and not asked again; the page reconnects to the
  extension when it loads (the extension may ask again). The menu switches
  either way at any time.

`test/nostr_test.js` reproduces the specification's worked packet byte for byte
through a stand-in extension; `test/ext_ask_smoke.py` checks the first-visit
question (asked, remembered, declined, no extension); `test/ext_smoke.py` drives it in a browser and has
a separate pure-Python BIP-340 verifier (`test/bip340_ref.py`) check what the page
signed.

## The engines behind the page

The page is one file on every platform; what differs is the engine behind
`spec/API-HTTP.md`: the Dart core's `WebChatApi` (the Android app's share
server and the Linux server edition) and the ESP32 firmware's `xwc`
(`common/xprs_webchat`). `contract/conformance.py <base-url>` is what says
they agree: a black-box run of the whole API (services, sessions, the
administrator and settings, moderators and their acts, hosted rooms, alerts)
with keys of its own, signed by the page's own crypto (`contract/sign.js`,
which needs node). Run it from the station's network against a station with
no administrator; it claims the station and releases it at the end. It is
the contract: a rule goes into the suite first, and every engine must pass.

## Working on it

```sh
python3 tool/build.py        # dist/chat_page.html and .gz
sh tool/test_crypto.sh       # the signing, against the spec
python3 test/smoke.py        # the page, in a browser, against three kinds of station
                             # (WEBCHAT_BROWSER=google-chrome if the snap Chromium dumps nothing)
python3 test/layout_smoke.py # the composer on a phone, under emulated bars (google-chrome)
node test/seal_test.js       # sealing, against known answers
node test/traffic_test.js    # the Traffic merge
node test/devices_test.js    # the Devices distance cell
node test/nostr_test.js      # the extension path, against the spec's worked packet
/usr/bin/python3 test/ext_smoke.py  # the extension in a browser, signature checked independently
/usr/bin/python3 test/dm_smoke.py   # a sealed DM both ways (needs python websockets)
```

Edit here, never in a generated copy. The firmware and the app each check their
copy against this repo when it is checked out next to them.
